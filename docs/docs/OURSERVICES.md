#### Detailed Workflow

##### Phase 1: Discovery & Strategy (1–4 weeks)

The foundation phase where business goals, audience needs, and technical requirements are defined before any design work begins. Discovery should consume 20–25% of total project time.

- **Stakeholder interviews** — Structured sessions with sales, marketing, leadership, and customer-facing teams to capture goals, constraints, and buyer intelligence
- **Competitive analysis** — Assessment of 3–5 competitor websites covering positioning, content quality, UX patterns, and conversion architecture
- **Analytics audit** — Review of GA4, Search Console, and CRM data (for redesigns) to understand current traffic, conversion performance, and audience behavior
- **Technical audit** — Current site architecture, platform capabilities, integration inventory, and technical debt assessment
- **Goal definition** — Primary business goal and main conversion defined; success metrics ranked and documented
- **Risk assessment** — Identify API dependencies, content migration challenges, GDPR/ADA compliance requirements, and timeline constraints

**Phase Gate:** Signed project brief and approved sitemap. No wireframes begin before this approval.

##### Phase 2: Information Architecture & UX (1–2 weeks)

Strategy becomes structure. The sitemap, user flows, and content plan are defined here.

- **Sitemap development** — Every page, its hierarchy, navigation placement, and URL structure documented
- **Wireframes** — Low-fidelity layouts for core templates (homepage, inner page, blog post, landing page, contact) showing element placement before visual design
- **User flow diagrams** — Visual maps showing how visitors navigate from entry point to conversion
- **Content plan** — Page-by-page outline of required content, assigned owners, and delivery deadlines
- **SEO keyword map** — Target keywords assigned to each page to prevent cannibalization
- **Navigation architecture** — Primary nav, footer, breadcrumbs, and URL structure defined

**Phase Gate:** Approved wireframes and content plan. No visual design begins before this approval.

##### Phase 3: Visual Design & Design System (2–6 weeks)

Brand, color, typography, imagery, and motion are applied to approved wireframes. This is where scope creep most commonly occurs.

- **Design system creation** — Typography scale, color palette, spacing system, component library (buttons, forms, cards, navigation, footers, modals)
- **High-fidelity mockups** — Desktop and mobile at minimum; tablet where required, using real content where possible
- **Responsive specifications** — Breakpoint behavior, interaction states (hover, focus, error, loading)
- **Accessibility considerations** — Contrast ratios verified (4.5:1 normal text, 3:1 large text), focus states designed, heading hierarchy planned
- **Design tokens** — Variables exported for color, spacing, typography, and border radii to ensure design-to-code parity
- **Revision rounds** — Defined number (typically 2–3) with written sign-off required at each milestone

**Phase Gate:** Approved visual design for all page templates. No development begins before this approval.

##### Phase 4: Development & Integration (3–8 weeks)

Approved designs become a functional website. Development happens on a staging environment — never on production.

- **Frontend build** — Component-first architecture matching the design system; responsive across all agreed breakpoints
- **CMS setup** — Platform configuration, user roles, content types, custom fields, and editorial workflows configured before content loading
- **Third-party integrations** — CRM, analytics, email marketing, ad pixels, form notifications, payment processors, booking systems, and custom APIs connected and tested
- **Performance optimization** — Image compression (WebP/AVIF), code minification, caching, Core Web Vitals tuning (LCP, INP, CLS)
- **SEO foundation** — Title tags, meta descriptions, schema markup, sitemap generation, robots.txt, canonical tags
- **Content loading** — Final approved copy, images, PDFs, and media populated; no placeholder content in staging

##### Phase 5: QA & Testing (1–3 weeks)

The most underestimated phase. Allocate 15–20% of total project timeline. Testing happens on staging across four layers:

- **Functional testing** — Every link, form, button, CTA, video, and integration verified end-to-end
- **Cross-browser & device testing** — Chrome, Safari, Firefox, Edge on desktop; iOS and Android on mobile and tablet; tested on real devices, not just DevTools
- **Performance testing** — Lighthouse audits on every key page; Core Web Vitals verified (LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1); throttled connection testing (3G/4G simulation)
- **Accessibility audit** — Three-layer approach:
  - *Automated*: axe DevTools and WAVE scans integrated into CI/CD pipeline (catches ~30–40% of issues)
  - *Manual*: Keyboard navigation, focus visibility, semantic structure, form label associations, color contrast verification
  - *Assistive technology*: Screen reader testing with NVDA + Firefox (Windows) and VoiceOver + Safari (macOS)
- **Content review** — Proofread every page; check for broken images, orphaned pages, incorrect metadata, placeholder content
- **Visual QA** — Staging build compared against approved Figma mockups to catch spacing, color, and layout mismatches

**Phase Gate:** QA-complete staging site review and client sign-off. No launch preparation begins before this approval.

##### Phase 6: Launch & Post-Launch (1 week + ongoing)

Structured execution with a checklist-driven approach.

- **Pre-launch checklist** — DNS configuration, SSL certificate verification, redirect mapping (301s for every old URL), robots.txt review, sitemap submission to Google Search Console
- **Analytics verification** — Confirm GA4 is tracking page views, events, and conversions correctly; set up real-time monitoring for first 24 hours
- **Go-live** — DNS cutover, smoke test, uptime and error alerts configured
- **Post-launch monitoring** — 48-hour performance watch; schedule visual QA pass one week after launch; 30-day monitoring period; 90-day performance review
- **Admin handover** — CMS training documentation, recorded walkthrough, content model documentation, and deployment process docs

#### Quality Standards & Compliance

**Core Web Vitals (2026 Thresholds — Unchanged):**

| Metric | Good | Needs Improvement | Poor |
|---|---|---|---|
| **LCP** (Largest Contentful Paint) | ≤ 2.5s | 2.5s – 4.0s | > 4.0s |
| **INP** (Interaction to Next Paint) | ≤ 200ms | 200ms – 500ms | > 500ms |
| **CLS** (Cumulative Layout Shift) | ≤ 0.1 | 0.1 – 0.25 | > 0.25 |

- Measured at the 75th percentile of real visitor data from Chrome User Experience Report (CrUX)
- All three metrics must hit "good" for a URL to pass — no partial credit
- Field data (real users) is what Google evaluates, not Lighthouse lab scores
- Only ~42% of mobile origins pass all three thresholds in 2026

**WCAG 2.1 AA Accessibility (Baseline; WCAG 2.2 Recommended):**

- **Perceivable** — Alt text on all images, color contrast ≥ 4.5:1 (normal text) / 3:1 (large text), captions and transcripts for media
- **Operable** — Full keyboard navigation, no keyboard traps, visible focus indicators, touch targets ≥ 24×24 CSS pixels (WCAG 2.5.8)
- **Understandable** — Proper heading hierarchy (single H1, no skipped levels), form labels with correct associations, error identification and suggestions
- **Robust** — Correct ARIA roles/states/properties, compatibility with NVDA, JAWS, and VoiceOver screen readers
- **Testing** — Three-layer approach: automated (axe/WAVE) + manual (keyboard, focus, semantics) + assistive technology (screen readers)

**Legal Context (2025–2026):**
- **ADA Title III** — US businesses open to the public; WCAG 2.1 AA via court precedent; enforceable now, no safe harbor
- **ADA Title II** — US state & local government; WCAG 2.1 AA; April 2026 deadline (<10K population: 2027)
- **European Accessibility Act (EAA)** — EU businesses & global companies serving EU; EN 301 549 / WCAG 2.1 AA; enforced since June 28, 2025

#### Detailed Workflow

##### Phase 1: Discovery & Offer Definition (3–5 days)

Before any design work, the offer, audience, and traffic source are locked. This is the cheapest place to be wrong.

- **Audience and intent mapping** — Define one primary audience, one problem state, and one expected transformation; map intent stage (cold, warm, decision-stage) to page strategy
- **Offer sharpening** — Define the single promise, the one action the page must drive, and what "qualified" means for downstream sales handoff
- **Voice-of-customer mining** — Pull language from reviews, sales calls, ad comments, and support tickets to ground copy in real buyer language
- **Traffic source alignment** — Document the ad campaign, email sequence, or organic source driving traffic; plan message-match between source and landing page
- **Funnel architecture** — Map the full page sequence (landing → checkout → upsell → thank-you) and define the conversion event at each step
- **Competitive analysis** — Screenshot and analyze 3–5 competitor landing pages for messaging patterns, proof placement, and CTA strategy

**Phase Gate:** Approved offer brief and funnel architecture document. No wireframes begin before this approval.

##### Phase 2: Wireframe & Copy (3–5 days)

Copy before design. The page is structured as an argument with a fixed sequence — not a creative layout exercise.

- **Fixed wireframe order** — Section sequence locked before copy or design begins:
  1. **Hero** — One promise, one subhead, one CTA
  2. **Belief shifts** — Three sections, each dismantling one assumption keeping the buyer on the status quo
  3. **Objection handling** — Name the real hesitation (price, switching cost, trust) and answer it before it festers
  4. **Proof** — Logos, numbers, named quotes; evidence placed after the argument that made the claim matter
  5. **Pricing teaser** — Enough to qualify and anchor, not the full table; remove fear of surprise, not close the deal here
  6. **FAQ** — The questions sales actually gets, answered in complete sentences; doubles as AI-answer surface
  7. **CTA** — One primary action, repeated; asked only after belief is shifted and objection is dead
- **Copy drafting** — Headline, subhead, proof blocks, objection responses, and CTA written and pressure-tested against the ad campaign driving the click
- **Form strategy** — Minimum fields for maximum routing value; each field must answer: does this change routing? does this change follow-up quality? can it be collected later?
- **Progressive qualification plan** — Define what's captured at first touch vs. what's gathered through confirmation flows or scheduled conversations

**Phase Gate:** Approved wireframe and copy document. No visual design begins before this approval.

##### Phase 3: Design & Build (4–7 days)

Copy and design run in parallel against one document — not in a relay. This single change compresses the build from weeks to days.

- **Visual design** — High-fidelity mockups in Figma; mobile-first; brand-adaptable components from the design system
- **First-screen architecture** — The hero must resolve three questions in seconds: is this relevant, what value can I expect, and what action should I take now
- **Trust system design** — Layered proof: short evidence near early claims, contextual social proof near mechanism blocks, reliability signals near final actions
- **Form and qualification UI** — Form fields tied to real routing decisions; conditional logic to keep forms relevant; mobile-optimized touch targets (minimum 44×44 pixels)
- **Page build** — Platform selected based on funnel requirements (see Tools section below); responsive across all breakpoints; Core Web Vitals budgeted (LCP < 1.8s mobile target for paid traffic pages)
- **Checkout flow build** (e-commerce funnels only) — Multi-step checkout, express payment buttons (Apple Pay, Google Pay, Shop Pay), address autocomplete, trust badges, running totals displayed

**Phase Gate:** Approved design and functional staging build. No tracking setup begins before this approval.

##### Phase 4: Tracking & Integrations (2–3 days)

Tracking is wired before launch, not after. Every page must generate clean data from day one.

- **GTM container configuration** — Event tracking for page views, form starts, form submissions, CTA clicks, scroll depth
- **GA4 setup** — Conversion events defined and verified; funnel visualization configured
- **Platform pixel setup** — Meta Pixel + CAPI (Conversions API), Google Ads conversion tracking, TikTok Pixel where relevant
- **CRM integration** — Lead routing and field mapping tested end-to-end; form submissions confirmed to reach the right inbox or pipeline
- **UTM parameter structure** — Standardized naming convention aligned with the campaign's traffic sources
- **E-commerce tracking** (where applicable) — Enhanced ecommerce, purchase events, revenue tracking, AOV measurement
- **Server-side tracking** — Where privacy regulations or browser restrictions require it, server-side GTM setup for data quality preservation

##### Phase 5: QA & Launch (2–3 days)

Quality checks are release gates, not optional reminders. A page does not scale traffic until critical checks pass.

- **Message clarity verification** — First-screen relevance confirmed; one dominant CTA path verified
- **Functional testing** — Every form, button, link, and integration tested end-to-end; checkout flow completed with test transactions
- **Mobile interaction checks** — Tap targets, form usability, sticky CTAs, viewport rendering on real devices
- **Performance audit** — Lighthouse run on every page variant; Core Web Vitals verified; throttled connection testing
- **Analytics validation** — Conversion events firing correctly in GA4, platform pixels, and CRM; data quality confirmed
- **Cross-browser testing** — Chrome, Safari, Firefox, Edge on desktop; iOS Safari and Android Chrome on mobile
- **Accessibility check** — Automated axe/WAVE scan plus manual keyboard navigation and focus verification

**Phase Gate:** QA-complete staging review and client sign-off. No traffic ramp begins before this approval.

##### Phase 6: Launch & Optimization Window (1 day launch + 30-day CRO window)

Launch is the beginning of an iterative cycle, not the finish line.

- **Go-live** — DNS/URL configuration, redirect setup if needed, analytics monitoring for first 24 hours
- **Traffic ramp** — Gradual traffic increase to validate tracking and server stability
- **30-day CRO window** — Heatmaps and session recordings analyzed; A/B variants shipped against the winning control; one-variable-per-cycle testing for clean insights
- **Performance report** — Conversion rate, cost per lead/acquisition, AOV (e-commerce), funnel drop-off analysis, and prioritized next-round recommendations

#### Funnel Mechanics: Order Bumps, Upsells & Downsells

For e-commerce and product funnel builds, three revenue mechanics are configured:

| Mechanic | Placement | Best Offer Type | Typical Take-Rate | AOV Impact |
|---|---|---|---|---|
| **Order Bump** | Inside checkout, before payment | Simple complement or practical add-on (under ~25% of cart total) | 15–30% | Low per bump, compounding across volume |
| **One-Click Upsell** | After payment, before thank-you page | Upgrade, bundle, replenishment, or next-step product | 5–15% | $5–$15 per transaction |
| **Downsell** | After upsell decline | Lower-priced fallback of the upsell offer | 3–10% | Captures revenue from would-be decline |

**Design principles:**
- Order bumps must be instantly understandable, clearly optional, and easy to accept or ignore — if the offer requires a feature comparison, it doesn't belong in checkout
- Post-purchase upsells have more room to make a case because the primary order is already complete; the card is on file; acceptance takes a single click
- Never auto-add to cart; trust lost at checkout is more expensive than a short-term AOV increase
- On mobile, confirm order bumps don't push the primary action too far down the page or create confusing tap targets

### Track A: Headless CMS Architecture

#### What It Is

A headless CMS fully separates the content management backend (database, editorial interface, content modeling) from the frontend presentation layer. Content is stored as structured data and delivered via API to any consuming frontend — website, mobile app, digital kiosk, voice assistant, or email template. The CMS has no native presentation layer; the frontend is built independently and fetches content through REST, GraphQL, or proprietary query APIs.

This is distinct from a **decoupled CMS** (e.g., WordPress with REST API), which retains a native frontend with templates but also exposes APIs for headless delivery. Headless is API-first with no built-in presentation; decoupled is a hybrid that offers both.

#### When to Choose Headless

- **Omnichannel delivery** — The same content must serve a website, mobile app, digital signage, or other surfaces from one source
- **Multi-brand portfolios** — Shared schemas with brand-level overrides, not forked models per site
- **Editorial independence** — Content editors restructure pages, add entries, and publish updates without waiting for a frontend deploy
- **Frontend flexibility** — Engineers can refactor the frontend, swap component libraries, or migrate hosting without touching content
- **Performance requirements** — Static generation (SSG) or incremental static regeneration (ISR) for sub-second page loads with content freshness
- **Complex content models** — Hundreds of content types, localization across dozens of locales, and governance requirements that monolithic CMSs can't handle

#### Detailed Workflow

##### Phase 1: Content Audit & Architecture (1–2 weeks)

- **Content inventory** — Audit existing content across all channels; document current content types, fields, relationships, and taxonomies
- **Content modeling** — Design structured content types as business entities (Product, Article, Offer, Policy), not page templates; use typed references over polymorphic blobs; define cardinality and ownership
- **Localization strategy** — Plan fallback locale hierarchy before launch; mark fields as non-localizable by default (dates, numeric values, references, slugs); opt in to localization only for translatable text
- **Governance model** — Define roles, approval workflows, validation rules, and compliance constraints at the schema level
- **API strategy** — Choose between REST (simpler, cacheable), GraphQL (flexible queries, client-specified fields), or proprietary query languages (e.g., Sanity's GROQ); document trade-offs
- **Multi-channel mapping** — Define which content types serve which channels; create channel-agnostic field names (e.g., `short_description`, not `mobile_description`)

**Phase Gate:** Approved content model and architecture document. No CMS setup begins before this approval.

##### Phase 2: CMS Setup & Configuration (1–3 weeks)

- **Platform provisioning** — CMS instance created; environments configured (development, staging, production)
- **Schema implementation** — Content types, fields, and relationships built in the CMS; validation rules enforced at the field and document level
- **Editorial interface customization** — Studio/dashboard configured to match the content team's workflow; custom components, dashboards, and validation added where needed
- **Role-based access control** — Granular permissions for editors, authors, administrators, and API consumers
- **Webhook configuration** — Event-driven webhooks set up to trigger frontend rebuilds, cache invalidation, or downstream syncs when content changes
- **Asset management** — Digital Asset Management (DAM) configured with rights metadata, expiration tracking, and automatic optimization
- **Preview environment** — Dedicated preview mode that fetches draft content through a separate API endpoint and renders it in the frontend; preview route secured against public access

**Phase Gate:** Approved CMS configuration with tested editorial workflows. No frontend integration begins before this approval.

##### Phase 3: Frontend Integration (2–5 weeks)

- **API integration** — Frontend connected to CMS delivery API; data fetching strategies chosen per route (SSG for static pages, ISR for occasionally-updated content, SSR for personalized/dynamic pages)
- **Content rendering** — Portable Text or structured rich text rendered to the appropriate output format (HTML, React components, mobile app views)
- **Cache architecture** — Multi-layer caching strategy: CDN-level for API responses, framework-level for rendered pages, tag-based invalidation for shared components, time-based revalidation for lower-priority content
- **Preview mode** — Frontend preview route implemented; editors can visualize draft content before publishing
- **Webhook-driven rebuilds** — Content changes trigger incremental rebuilds of only affected pages, not full site rebuilds
- **Search integration** — Full-text search configured (Algolia, Meilisearch, or native CMS search) with content sync via webhooks or event streams
- **Performance optimization** — Sub-100ms content reads via CDN; image optimization with on-the-fly format conversion, resizing, and lazy loading

##### Phase 4: QA, Migration & Launch (1–3 weeks)

- **Content migration** — Existing content mapped to new schema and migrated; data integrity verified
- **Editorial QA** — Content editors test the full workflow: create, edit, preview, schedule, publish, and unpublish
- **API performance testing** — Response times verified under load; CDN caching validated; cache invalidation tested
- **Multi-channel validation** — Content rendered correctly across all target channels (web, mobile, etc.)
- **Security audit** — API tokens scoped per environment; access control verified; preview routes secured
- **Launch** — DNS cutover, redirect mapping, sitemap submission, analytics verification

### Track B: Progressive Web App Development

#### What It Is

A Progressive Web App is a web application built with standard web technologies (HTML, CSS, JavaScript) that uses modern browser APIs to deliver app-like capabilities: installability, offline support, push notifications, background sync, and device hardware access. A single PWA codebase runs on any platform with a modern browser — iOS, Android, desktop, tablet.

PWAs are built on three web platform primitives:
1. **Service Workers** — JavaScript files running in a separate thread that intercept network requests, manage caches, handle push events, and run background tasks even when the app is closed
2. **Web App Manifest** — JSON file describing the app: name, icons, theme color, start URL, display mode; enables installation to home screen with a native-app-like launch experience
3. **HTTPS** — Hard requirement for all service worker features; ensures the intercepting proxy cannot be tampered with

#### When to Choose PWA vs. Native

| Factor | PWA | Native App |
|---|---|---|
| **Development cost** | $80K–$150K (1 codebase) | $200K–$400K+ (iOS + Android + web) |
| **Time to market** | 2–3 months | 4–8 months (per platform) |
| **Updates** | Instant — deploy to server, users get update on next visit | 1–2 week App Store review process |
| **Distribution** | URL sharing, Google Search indexable, no app store required | App Store / Google Play (30% commission, approval process) |
| **Offline capability** | Full functionality with service workers and caching | Deeper offline storage and OS integration |
| **Push notifications** | Supported on Chrome, Edge, Firefox, Safari (iOS 16.4+) | Full native support on all platforms |
| **Device APIs** | Camera, GPS, Bluetooth (Chrome), NFC (Android), WebAuthn, accelerometer, clipboard | Full access to all platform APIs, HealthKit, ARKit, biometric, background audio |
| **SEO** | Crawlable and indexable by search engines | Not discoverable via web search |
| **User friction** | 80–90% of visitors engage (no installation barrier) | 30–40% conversion (requires download and install) |

**PWA is the default choice in 2026 for:** internal business tools, field service applications, B2B customer portals, e-commerce, content platforms, healthcare/clinical workflows, CRM/operations dashboards, and any application where App Store distribution isn't a core go-to-market strategy.

**Native remains the right choice for:** games and graphics-intensive apps, deep hardware integration (Bluetooth LE pairing, real-time sensors, complex audio/video), App Store discoverability as a primary acquisition channel, and apps requiring platform-specific features (HomeKit, HealthKit, lock screen widgets).

#### Detailed Workflow

##### Phase 1: Discovery & Architecture (1–2 weeks)

- **Use case definition** — Define the core user journeys, offline requirements, and device capabilities needed
- **Platform assessment** — Verify target browsers support required APIs (service workers, push notifications, background sync, Web Bluetooth, etc.)
- **App shell architecture** — Separate UI shell (navigation, sidebars, layout) from content; shell is cached aggressively for instant repeat visits; content fetched dynamically
- **Caching strategy planning** — Define per-resource-type strategies:

| Strategy | How It Works | Best For |
|---|---|---|
| **Cache First** | Serve from cache; fetch from network only if not cached | App shell, fonts, versioned static assets |
| **Network First** | Try network; fall back to cache on failure | API data, user-specific content |
| **Stale While Revalidate** | Serve cache immediately; update cache in background | Images, blog posts, product listings |
| **Cache Only** | Always serve from cache; never fetch network | Precached assets, offline-critical content |

- **Offline-first UX design** — Design every user flow assuming connectivity is unreliable; show cached data immediately, sync in background, communicate sync status clearly
- **Push notification strategy** — Define notification types, trigger conditions, and permission request timing

**Phase Gate:** Approved architecture document and caching strategy. No development begins before this approval.

##### Phase 2: Core Development (3–6 weeks)

- **Service worker implementation** — Registration, install event (precaching app shell), activate event (cache cleanup and migrations), fetch event handler (routing to appropriate caching strategy)
- **Web App Manifest** — Name, short name, icons (192px and 512px minimum), theme color, background color, start URL, display mode (standalone or fullscreen), splash screen configuration
- **App shell build** — Navigation, layout, and core UI components built and precached; sub-1-second repeat visit load times regardless of network conditions
- **Offline data layer** — IndexedDB for structured offline storage; background sync API for deferred operations when connectivity resumes
- **Push notifications** — Notification permission flow; push event handler in service worker; notification display and click-through routing
- **Responsive UI** — Mobile-first design; adaptive layouts for phone, tablet, and desktop; touch-optimized interactions (44×44px minimum tap targets)
- **Hardware API integration** (where needed) — Camera, geolocation, accelerometer, WebAuthn (biometric authentication), Web Bluetooth, Web NFC

##### Phase 3: Advanced Features (2–4 weeks, optional)

- **Background sync** — Deferred actions that execute when connectivity is restored (e.g., form submissions, data uploads)
- **Periodic background sync** — Scheduled content refresh for time-sensitive applications (experimental; Chrome-only as of 2026)
- **Share API integration** — Native share sheet integration for cross-app content sharing
- **File system access** — Read/write access to user-selected files (Chrome/Edge; limited Safari support)
- **App store packaging** (optional) — PWA packaged via TWA (Trusted Web Activity) for Google Play distribution; PWA Builder for Microsoft Store

##### Phase 4: QA & Launch (1–2 weeks)

- **Service worker lifecycle testing** — Install, activate, update, and skip-waiting behaviors verified; stale cache scenarios tested
- **Offline testing** — App fully functional with no network; graceful degradation verified for each caching strategy
- **Cross-browser testing** — Chrome, Edge, Firefox, Safari on desktop; iOS Safari and Android Chrome on mobile; feature detection verified for each API
- **Installability verification** — Lighthouse PWA audit passed; install prompt triggers correctly; installed app launches in standalone mode
- **Performance audit** — Lighthouse scores: 90+ Performance, 100 PWA; Core Web Vitals verified; repeat-visit load times under 600ms
- **Push notification testing** — Notifications received on all target platforms; click-through routing verified
- **Security audit** — HTTPS enforced; service worker scope verified; preview routes secured

#### Why Care Plans Matter

A website is not a one-time deliverable; it decays on multiple clocks simultaneously. Security vulnerabilities surface as CVEs, dependencies drift toward end-of-life, performance regresses as content accumulates, and accessibility conformance erodes as new templates are added. Without structured maintenance, a custom build rots quietly — and the first sign of trouble is often a Google flag, a broken checkout, or a security breach.

A care plan turns unpredictable, reactive firefighting into predictable, proactive stewardship. It also creates clear boundaries: with no plan, clients reach out for small fixes and expect them to be free. With a plan, both sides have shared rules about what is covered and what is billable.

<summary><strong>Conversion Rate Optimization (CRO) — Full Profile</strong></summary>

Systematic A/B and multivariate testing, heatmaps and session recordings, and iterative landing page refinement. Offered as a **Retainer** engagement with monthly billing and continuous optimization cycles. CRO is a program, not a project — a repeating loop of research → hypothesis → prioritize → test → analyze → iterate that compounds learnings over time. The longer the engagement runs, the faster results accumulate because each test informs the next.

**Core premise:** Improving conversion rate multiplies the return on every other channel's spend. A 36% uplift on a landing page becomes the new baseline; the next test compounds on top of it. Over a full engagement, cumulative improvements can reach several hundred percent — but only through disciplined process, not random experimentation.

#### Prerequisites

CRO is not the right service for every client. Before engagement:

- **Traffic volume** — Minimum ~10,000 monthly sessions to run valid A/B tests; ideally 50,000+ for tests to reach significance in reasonable timeframes. Below 10K sessions, a project-based UX audit is more cost-effective than a testing retainer.
- **Conversion tracking** — The conversion being optimized must be tracked accurately. If tracking is broken (double-counted, missing on mobile, polluting Unassigned), test results measure a broken instrument. Verify tracking before running a single test.
- **UX foundation** — Structural UX problems (confusing layout, missing trust signals, buried CTAs) should be addressed first. CRO compounds on a solid foundation; it doesn't fix fundamental design problems.
- **Internal capacity** — Client team must have bandwidth to review test results, approve variants, and participate in prioritization decisions. Without engaged stakeholders, the program slows and value drops.

#### The CRO Loop

Every engagement follows a continuous four-step loop:

1. **Research** — Find where to focus, with evidence. Quantitative: GA4 funnels, drop-off pages, high-traffic/low-conversion pages. Qualitative: heatmaps, session recordings, user surveys, support ticket analysis, review mining. Never start from "I have an idea for the homepage."

2. **Hypothesis** — Frame it testably: "Because [evidence], we believe [change] will [effect] for [audience], measured by [metric]." A hypothesis without evidence is a guess. Document the mechanism — why it's expected to work — so the reasoning can be interrogated if the result surprises.

3. **Prioritize** — Score every hypothesis using a framework (ICE, PIE, or PXL — see below) to rank by leverage, not by whoever's loudest. Account for traffic feasibility: a high-impact hypothesis on a low-traffic page may never reach significance.

4. **Test & Analyze** — Run a clean A/B experiment with predetermined sample size and duration. One variable per test where possible for unambiguous attribution. Significant win → ship it and build on it. No effect or loss → that's a learning, not a failure; feed it back into research. The compounding is in the iteration.

#### Prioritization Frameworks

Three frameworks are used to rank hypotheses. The framework matters less than using one consistently:

| Framework | Factors | Scoring | Best For |
|---|---|---|---|
| **ICE** | Impact, Confidence, Ease | 1–10 each; multiply or average | High-volume triage of many ideas; small teams needing speed |
| **PIE** | Potential, Importance, Ease | 1–10 each; average | CRO backlogs where page value and traffic matter; page-level prioritization |
| **PXL** | ~10 fixed criteria (evidence-based, binary) | Sum points; mostly yes/no questions | Mature programs with research data; teams wanting to reduce subjectivity |

**Practical default:** Use ICE to triage a long backlog down to a shortlist quickly, then run PXL on the shortlist before committing engineering time.

**Calibration rule:** Review the last 20 test results. Calculate actual win rate (industry average: 20–33%) and median lift. Use those numbers as ceiling constraints on future Impact scores. Scoring any single test as 9/10 impact when historical win rate is 25% and average lift is 8% is statistically delusional.

#### Experimentation Discipline

The bottleneck in CRO is rigor, not tooling. A rigorous program with basic tools beats a sloppy one with sophisticated software every time.

**Statistical Requirements:**
- **Sample size** — Calculated before launch using baseline rate, MDE (minimum detectable effect), significance level (95%), and power (80%). The MDE is the single biggest lever on sample size because it enters the formula squared — halving the MDE roughly quadruples the visitors needed.
- **Test duration** — Run for at least one full business cycle (usually 2+ weeks) so weekday/weekend and pay-cycle effects wash out. Never stop a test early because it looks significant — early "significance" is usually noise.
- **Statistical significance** — 95% confidence threshold (alpha = 0.05). This means a 5% chance of false positive on a true null.
- **Statistical power** — 80% (beta = 0.20). Underpowered tests are the quiet killer: a flat, inconclusive result gets misread as "the change did nothing" when the truth is "the test could never have seen it."
- **One primary metric** — Commit to a single Overall Evaluation Criterion before launch. Tracking ten metrics and reporting whichever one moved is how teams mine noise for a story.
- **Guardrail metrics** — Define metrics that should not regress (bounce rate, page load speed, error rate, refund rate, support tickets). A variation that improves sign-ups but damages performance or SEO is not a reliable win.
- **SRM checks** — Monitor for sample ratio mismatch. A 50/50 experiment getting 45/55 traffic split signals tracking failures, bot traffic, or allocation issues.

**Cardinal Sins to Avoid:**
- **Peeking** — Checking daily and calling it the moment it looks significant; the #1 way to ship false wins
- **Too-small sample** — A test that "won" on 40 conversions per variant proved nothing
- **Too-short duration** — A test that only saw Tuesdays has not seen your users
- **Testing trivia** — Button colors rarely move revenue; test things tied to real friction (the offer, the form, the page structure)
- **Multiple-variant fishing** — Testing ten variants at once and crowning the winner is how randomness wins
- **No losing-test archive** — Teams re-run dead ideas every time someone new joins; keep a one-line log: hypothesis, result, date

#### Integration Architecture Patterns

Three primary approaches, chosen per integration based on data volume, transformation complexity, team capacity, and rate of change:

| Pattern | How It Works | Best For | Trade-off |
|---|---|---|---|
| **Direct / Native** | Pre-built connector or native integration from platform App Store | Standard data flows between well-known systems (orders, inventory, customers); no engineering resources needed | Deploys in days; limited customization; can't handle business-specific logic |
| **iPaaS (Integration Platform as a Service)** | Cloud middleware with pre-built connectors, data transformation, and flow orchestration | Multi-system routing with moderate transformation; teams without dedicated engineering | Monthly subscription cost; vendor lock-in; limited at high volume or complex logic |
| **Custom API Integration** | Built from scratch using each platform's API; maximum flexibility | Business-specific logic, unusual routing rules, proprietary systems with no public connector | Most resource-intensive; requires ongoing maintenance as APIs version and business rules change |

**Decision framework — four criteria:**
1. **Data volume and frequency** — How many records move per day, and how close to real time? High-volume, high-frequency flows justify heavier-duty tooling.
2. **Transformation complexity** — Does data pass through unchanged, or does it need reshaping, enrichment, or conditional logic?
3. **Team technical capacity** — Are there engineers to build and maintain, or must it run without them?
4. **Rate of change** — How frequently will the integration logic itself change? Stable flows favor prebuilt connectors; fast-changing logic favors tools the team can modify quickly.

#### Detailed Workflow

##### Phase 1: Discovery & Architecture (1–2 weeks)

- **Systems inventory** — Catalog every system to be integrated: product, API type (REST, GraphQL, SOAP), auth method (OAuth2, API key), real-time capability (webhooks, streams), rate limits, webhook reliability, and data contract docs (OpenAPI/Swagger)
- **Data flow mapping** — Document what data moves where, in which direction, at what frequency, and with what transformation; create a visual flow diagram
- **Canonical data model** — Define a canonical entity model (e.g., `Customer`, `Order`, `Booking`) with mapped fields from each system; define identity match rules (deterministic by email/phone, probabilistic by name+DOB+address)
- **Conflict resolution rules** — Define which system is the source of truth per field; latest-update-wins vs. system-priority-wins; track provenance metadata (`source_system`, `source_id`, `last_synced_at`)
- **Integration pattern selection** — Choose direct/iPaaS/custom per flow using the four-criteria decision framework
- **Security and compliance review** — Identify data classification (PII, PCI, PHI), required encryption, consent requirements, and regulatory constraints (GDPR, CCPA, HIPAA, PCI DSS)
- **Error handling strategy** — Define error categories (validation, auth, not found, rate limited, transient, unknown), retry policies, circuit breakers, fallback mechanisms, and dead-letter queue paths

**Phase Gate:** Approved architecture document and data flow diagram. No development begins before this approval.

##### Phase 2: Development & Configuration (2–6 weeks)

- **Authentication setup** — OAuth2 client credentials (server-to-server), API keys, or HMAC signatures; token refresh logic; secure secret storage in environment variables or vault
- **API client implementation** — Typed API clients with retry logic, timeout enforcement (5–10 seconds baseline), rate-limit awareness, and pagination handling
- **Webhook endpoints** — HTTPS endpoints with signature verification (HMAC or RFC 9421), rapid 2xx acknowledgement before processing, async processing queue, idempotency key storage
- **Data transformation layer** — Field mapping, type conversion, enrichment, and conditional logic at system boundaries; tolerant readers that ignore unknown fields
- **Bi-directional sync logic** — Conflict detection, deduplication, and merge rules; per-entity write serialization to prevent race conditions
- **Error handling implementation** — Exponential backoff with jitter for transient failures; circuit breakers to prevent cascade failures; dead-letter queue for unrecoverable failures; structured error logging with request IDs
- **Rate limiting controls** — Client-side throttling to stay within API quotas; concurrency caps; queue-based processing for batch operations; monitor `Retry-After` headers
- **Observability layer** — Request/response logging (without sensitive data), structured event logs, alerting on failure rates, latency tracking, and audit trail for regulated environments

##### Phase 3: Testing & QA (1–2 weeks)

- **Integration testing** — End-to-end flow testing: trigger event in source system → verify data arrives correctly in destination system
- **Webhook testing** — Signature verification tested with real and forged payloads; duplicate delivery handling verified; retry behavior tested under simulated failures
- **Error scenario testing** — Simulate 429 rate limits, 500 server errors, network timeouts, expired tokens, and malformed payloads; verify retry, circuit breaker, and DLQ behavior
- **Data integrity testing** — Verify field mapping accuracy, conflict resolution correctness, and no data loss across sync cycles
- **Performance testing** — Verify throughput under expected load; test batch processing capacity; confirm rate-limit compliance
- **Security testing** — Verify no secrets in client-side code; confirm HTTPS enforcement; validate webhook signature verification; test with revoked tokens

##### Phase 4: Deployment & Monitoring (1 week)

- **Staged rollout** — Deploy to staging; verify with production data in read-only mode; progressively enable write operations
- **Monitoring configuration** — Alerts for failure rate spikes, latency anomalies, auth failures, rate-limit approaches, and DLQ depth
- **Runbook creation** — Document common failure scenarios, diagnostic steps, and remediation procedures
- **Client handoff** — Architecture documentation, API credentials handoff, monitoring dashboard access, and operational training

#### Quality Standards

**Reliability:**
- Idempotency keys on all write operations — duplicate deliveries must not create duplicate records, double charges, or repeated updates
- Exponential backoff with jitter on all retries — prevents thundering herd and retry storms
- Circuit breakers on all external dependencies — prevents cascade failures when a third-party is slow or unavailable
- Dead-letter queue for unrecoverable failures — no silent drops; every failed event is stored and replayable
- Timeouts on all upstream calls (5–10 seconds baseline) — no hanging requests
- Per-entity write serialization — prevents race conditions in bi-directional sync

**Security:**
- No third-party credentials in client-side code — all API keys and OAuth tokens stored server-side in environment variables or vault
- HTTPS enforced on all webhook endpoints — no HTTP
- Webhook signature verification (HMAC or RFC 9421) — never skip in production
- OAuth2 with short-lived access tokens (typically 1 hour) and refresh token rotation
- Timestamp validation on webhooks (5-minute tolerance window) to prevent replay attacks
- Dual-active signing secrets during rotation windows (24–48 hours) to avoid stranding in-flight retries
- Data classification and encryption per regulatory requirements (GDPR, CCPA, HIPAA, PCI DSS)

**Observability:**
- Structured logging with request IDs for traceability across systems
- Alerting on failure rate spikes, auth failures, rate-limit approaches, and DLQ depth
- Audit trail for regulated environments — exportable delivery logs
- Monitoring dashboard accessible to client team
- Runbook for common failure scenarios

**Data Integrity:**
- Canonical data model with documented field mappings
- Conflict resolution rules defined per field (source-of-truth hierarchy)
- Provenance metadata tracked (`source_system`, `source_id`, `last_synced_at`)
- No data loss across sync cycles — verified in QA
- Tolerant readers that ignore unknown fields — survives vendor schema additions

#### Pricing Factors

- **Number of systems** — Each additional system adds discovery, development, testing, and monitoring scope
- **Integration pattern** — Direct/native (lowest cost) vs. iPaaS (monthly subscription + setup) vs. custom API (highest cost, most flexible)
- **Directionality** — One-way sync (simpler) vs. bi-directional sync (conflict detection, merge logic, per-entity serialization)
- **Real-time requirements** — Polling (simpler, slower) vs. webhook-driven (faster, more engineering overhead for signature verification, idempotency, retry handling)
- **Data transformation complexity** — Pass-through (minimal) vs. field mapping + type conversion vs. conditional logic + enrichment + multi-step orchestration
- **Compliance requirements** — PCI DSS (payment data), HIPAA (health data), GDPR/CCPA (PII); each adds security review, encryption, audit trail, and testing overhead
- **Volume and rate limits** — High-volume integrations require queue-based processing, rate-limit controls, and more robust error handling
- **Legacy system involvement** — Custom adapters, data migration, and limited documentation increase scope
- **Ongoing maintenance** — APIs version and deprecate; business rules change; vendor outages require debugging; budget for the full lifecycle, not just the build (MuleSoft research: IT teams spend 36% of their time on integration maintenance)
